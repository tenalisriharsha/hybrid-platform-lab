# Hybrid Platform Lab - Build Progress

STATUS: IN_PROGRESS

## Vision

A self-service VM platform for development and validation environments across VMware vSphere, Proxmox VE and Azure. A REST API validates each request against approved templates. A PowerCLI module provisions and manages vSphere VMs, Terraform modules cover Proxmox and Azure, Ansible and PowerShell apply Linux and Windows Server baselines, and GitHub Actions tests everything against vcsim and mocked providers. WHAT TO BUILD: (1) FastAPI service: POST, GET and DELETE on /environments with template and size validation and owner and expiry fields, plus a /metrics endpoint for Prometheus. The vSphere backend calls the PowerCLI module through pwsh. The Proxmox and Azure backends only render tfvars and run terraform plan, never apply. (2) PowerCLI module with 3 cmdlets: New-LabVM (clone a VM from a template, attach a port group, mark it), Get-VMInventoryReport (inventory plus drift against a desired-state file) and Invoke-SnapshotPolicy (snapshot lifecycle with -WhatIf and -Confirm, refusing VMs marked protected). Tested with Pester against vcsim in both vCenter mode and standalone-ESXi mode. VCSIM FACTS ALREADY VERIFIED ON THIS MACHINE: the vmware/vcsim image is amd64 and runs emulated here, start it as docker run -p 8989:8989 vmware/vcsim -l :8989 for vCenter mode and add -esx for standalone ESXi mode; Connect-VIServer 127.0.0.1 -Port 8989 -User user -Password pass -Force works; Get-VM, Get-VMHost, Get-Datastore, Get-VirtualPortGroup, New-Snapshot, Get-Snapshot, Remove-Snapshot, New-VM -VM (clone) and Get-NetworkAdapter work in both modes; PowerCLI TAGS DO NOT WORK on vcsim (New-TagCategory fails with a missing lookup service in vCenter mode and tags are unsupported on a standalone ESXi host), and custom attributes only work in vCenter mode. So implement the protected, owner and expiry markers behind one small abstraction: use vSphere tags when the server supports them, otherwise fall back to a marker line in the VM Notes (Set-VM -Notes), which works in both modes, and document that real vCenter uses tags. Never claim vcsim proves behaviour it does not simulate. (3) Terraform: modules/proxmox-vm using the bpg/proxmox provider and modules/azure-vm using azurerm, dev and validation environment folders, and native terraform test files using mock_provider; no real credentials, never apply. (4) Ansible: one linux-baseline role (users, SSH hardening, packages, services, node_exporter) run in CI against a Docker container (containers have no systemd, so guard service tasks with a variable), checked with ansible-lint and an idempotence check where the second run changes nothing. (5) PowerShell: a Windows Server baseline script (services, features, firewall checks) written so its logic is unit-testable with mocks, tested with Pester on GitHub's windows-latest runner (it cannot run on this Mac, so verify the Windows job through CI and fix what it reports). (6) Docs: RUNBOOK.md covering failed provisioning, exhausted capacity, rollback and a failed automation job; docs/modernization.md with a short decision table of which workloads stay on VMware and which move to containers or Azure. (7) CI: one GitHub Actions workflow with five jobs: pytest and ruff, Pester with vcsim as a service container, terraform test, Ansible, and Windows Pester. PREVIEWS: Swagger UI of the API, and terminal captures from real runs of the Pester suite against vcsim, a drift report, Invoke-SnapshotPolicy -WhatIf refusing a protected VM, terraform test, and the Ansible run with ansible-lint. Cut from scope: Packer, Molecule, k6, DSC and IIS, Proxmox on KVM, pyVmomi, a separate exporter, a GitHub Projects board. The README must state plainly that nothing touches a real vSphere, Proxmox or Azure and that everything is tested against vcsim, mocked providers and plans.

- **`api/app/backends/vsphere.py`** (`VSphereBackend`) - the real `"vsphere"` backend. `provision()`/`deprovision()` shell out via `subprocess.run([pwsh, ..., "-File", script, *args])` (a real file + argument list, never a `-Command` string built by interpolating request data - avoids injection entirely rather than trying to escape it) to `powercli/scripts/Invoke-VSphereProvision.ps1`/`Invoke-VSphereDeprovision.ps1`. ### Design notes to carry forward

- **Backend abstraction.** `app/backends/__init__.py`'s `_BACKENDS` dict is keyed by `"vsphere"/"proxmox"/"azure"`. Phase 3 should replace the `"proxmox"`/`"azure"` `SimulatedBackend` entries with real backends that render Terraform tfvars and run `terraform plan` only (never apply) - likely via the same `subprocess.run([..., "-File"/positional args, ...])` pattern `vsphere.py` uses (no shell string interpolation of request data). The router and store do not need to change.
- `ProvisioningError` (in `app/backends/base.py`) maps to a 502 on both create and delete - reuse it for `terraform plan` failures too.
- The catalog (`app/catalog.py`) is the single source of truth for template → backend mapping and size → spec. `vsphere.py`'s `source_vm` + `HYBRID_LAB_VSPHERE_TEMPLATE_OVERRIDES` pattern (a catalog field for the "real" value, overridable via env var for environments - and tests - where it differs) is a reasonable template for whatever Proxmox/Azure need (an image reference, a resource group, etc.).
- Metrics use a registry scoped to the FastAPI app instance (`app.state.metrics.registry`), not `prometheus_client`'s global default registry - keep doing this so future tests that spin up multiple app instances don't collide.
- **Mocking compiled PowerCLI cmdlets in Pester doesn't work** if the cmdlet has a strongly-typed parameter (e.g. `Set-VM -VM : VirtualMachine[]`) - Pester's mock preserves that type constraint, so a plain test double gets rejected before the mock body ever runs. Wrap the call in your own loosely-typed private function and mock that instead (see `Set-LabVMNotesMarker`). Only matters when adding new unit tests against real PowerCLI cmdlets, not against vcsim (vcsim tests pass real objects, no mocking involved).
- **vcsim quirk:** a VM's `VirtualPortGroup` object, once resolved via `Get-VirtualPortGroup`, can't be handed to `Set-NetworkAdapter -PortGroup` reliably - standard portgroups sharing a name across hosts also share vcsim's internal `Key` string, so PowerCLI's own re-resolution becomes ambiguous even for a single already-resolved object. Use `Set-NetworkAdapter -NetworkName '<name>'` (a string) instead, which resolves scoped to the adapter's own VM/host and has no such issue; see `New-LabVM.ps1`.
