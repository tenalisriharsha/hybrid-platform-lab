# Hybrid Platform Lab - Build Progress

STATUS: IN_PROGRESS

## Vision

A self-service VM platform for development and validation environments across VMware vSphere, Proxmox VE and Azure. A REST API validates each request against approved templates. A PowerCLI module provisions and manages vSphere VMs, Terraform modules cover Proxmox and Azure, Ansible and PowerShell apply Linux and Windows Server baselines, and GitHub Actions tests everything against vcsim and mocked providers. WHAT TO BUILD: (1) FastAPI service: POST, GET and DELETE on /environments with template and size validation and owner and expiry fields, plus a /metrics endpoint for Prometheus. The vSphere backend calls the PowerCLI module through pwsh. The Proxmox and Azure backends only render tfvars and run terraform plan, never apply. (2) PowerCLI module with 3 cmdlets: New-LabVM (clone a VM from a template, attach a port group, mark it), Get-VMInventoryReport (inventory plus drift against a desired-state file) and Invoke-SnapshotPolicy (snapshot lifecycle with -WhatIf and -Confirm, refusing VMs marked protected). Tested with Pester against vcsim in both vCenter mode and standalone-ESXi mode. VCSIM FACTS ALREADY VERIFIED ON THIS MACHINE: the vmware/vcsim image is amd64 and runs emulated here, start it as docker run -p 8989:8989 vmware/vcsim -l :8989 for vCenter mode and add -esx for standalone ESXi mode; Connect-VIServer 127.0.0.1 -Port 8989 -User user -Password pass -Force works; Get-VM, Get-VMHost, Get-Datastore, Get-VirtualPortGroup, New-Snapshot, Get-Snapshot, Remove-Snapshot, New-VM -VM (clone) and Get-NetworkAdapter work in both modes; PowerCLI TAGS DO NOT WORK on vcsim (New-TagCategory fails with a missing lookup service in vCenter mode and tags are unsupported on a standalone ESXi host), and custom attributes only work in vCenter mode. So implement the protected, owner and expiry markers behind one small abstraction: use vSphere tags when the server supports them, otherwise fall back to a marker line in the VM Notes (Set-VM -Notes), which works in both modes, and document that real vCenter uses tags. Never claim vcsim proves behaviour it does not simulate. (3) Terraform: modules/proxmox-vm using the bpg/proxmox provider and modules/azure-vm using azurerm, dev and validation environment folders, and native terraform test files using mock_provider; no real credentials, never apply. (4) Ansible: one linux-baseline role (users, SSH hardening, packages, services, node_exporter) run in CI against a Docker container (containers have no systemd, so guard service tasks with a variable), checked with ansible-lint and an idempotence check where the second run changes nothing. (5) PowerShell: a Windows Server baseline script (services, features, firewall checks) written so its logic is unit-testable with mocks, tested with Pester on GitHub's windows-latest runner (it cannot run on this Mac, so verify the Windows job through CI and fix what it reports). (6) Docs: RUNBOOK.md covering failed provisioning, exhausted capacity, rollback and a failed automation job; docs/modernization.md with a short decision table of which workloads stay on VMware and which move to containers or Azure. (7) CI: one GitHub Actions workflow with five jobs: pytest and ruff, Pester with vcsim as a service container, terraform test, Ansible, and Windows Pester. PREVIEWS: Swagger UI of the API, and terminal captures from real runs of the Pester suite against vcsim, a drift report, Invoke-SnapshotPolicy -WhatIf refusing a protected VM, terraform test, and the Ansible run with ansible-lint. Cut from scope: Packer, Molecule, k6, DSC and IIS, Proxmox on KVM, pyVmomi, a separate exporter, a GitHub Projects board. The README must state plainly that nothing touches a real vSphere, Proxmox or Azure and that everything is tested against vcsim, mocked providers and plans.

- **`api/app/backends/vsphere.py`** (`VSphereBackend`) - the real `"vsphere"` backend. `provision()`/`deprovision()` shell out via `subprocess.run([pwsh, ..., "-File", script, *args])` (a real file + argument list, never a `-Command` string built by interpolating request data - avoids injection entirely rather than trying to escape it) to `powercli/scripts/Invoke-VSphereProvision.ps1`/`Invoke-VSphereDeprovision.ps1`. ### What Phase 3 added

- **`terraform/modules/proxmox-vm/`** - clones a VM from a Proxmox template (`bpg/proxmox`'s `proxmox_virtual_environment_vm` resource, `clone { vm_id = ... }`); owner/expiry/env are encoded as tags (`hybrid-lab`, `owner:...`, `expiry:...`, plus whatever `extra_tags` the caller passes), mirroring the vSphere Notes-marker fallback in spirit. **`terraform/modules/azure-vm/`** - a dedicated resource group + vnet/subnet + NIC + `azurerm_linux_virtual_machine` (SSH key only, `disable_password_authentication = true`), owner/expiry/env as resource group tags. Both have `versions.tf`/`variables.tf`/`main.tf`/`outputs.tf` and a `tests/*.tftest.hcl` suite (6 runs each, all passing) using `mock_provider` - no real credentials needed, `terraform test` just needs the real provider's schema (downloaded once by `terraform init`, no API calls made).
- **`terraform/environments/{dev,validation}/{proxmox,azure}/`** - each wires the matching module to a `provider` block that is **deliberately empty** (`provider "proxmox" {}` / `provider "azurerm" { features {} }`) and relies entirely on the provider's own standard environment variables (`PROXMOX_VE_*`, `ARM_*`) for credentials - never a tfvars file. **dev** is what the API backends plan against, tagged `env:dev`/`env=dev`. **validation** adds a governance gate: an `approved` variable (default `false`) with a `validation` block that fails *before the provider is ever configured* unless `approved = true` - a `terraform test` (`tests/approval-gate.tftest.hcl`, 2 runs each) confirms both the refusal and the success path (via `mock_provider`, since the approved run does reach the module/provider).
- **`api/app/backends/terraform_utils.py`** - the shared plumbing both new backends use: `environment_dir()`, `render_tfvars_file()` (writes a real `.tfvars.json` temp file - Terraform accepts JSON tfvars natively, no HCL generation needed), `plan()` (lazy `terraform init` if `.terraform/` is missing, then `terraform plan` - never `apply` - raising `ProvisioningError` with the real terraform stderr on any failure), and `plan_summary()` (regex-extracts the `Plan: N to add, N to change, N to destroy.` line for the API response's `detail` field).
- **`api/app/backends/proxmox.py`** (`ProxmoxBackend`) and **`api/app/backends/azure.py`** (`AzureBackend`) - both follow the exact shape of `vsphere.py`: a `_config()` that checks required env vars and raises `ProvisioningError` with a clear "not configured" message if any are missing, a `provision()` that renders tfvars + runs `terraform plan` + returns a `ProvisionResult`, and a `deprovision()` that is a deliberate **no-op** - since `apply` never ran, there is no real resource behind `backend_ref` to tear down (this is different from the vSphere backend, which does destroy something real on vcsim). `app/backends/__init__.py`'s `_proxmox_backend()`/`_azure_backend()` pick the real backend only once `HYBRID_LAB_PROXMOX_ENDPOINT`/`HYBRID_LAB_AZURE_SUBSCRIPTION_ID` are set, else fall back to `SimulatedBackend` - same pattern as `_vsphere_backend()`.
- `api/catalog.py`'s proxmox/azure `TEMPLATES` entries gained `proxmox_template_vm_id` (an int VMID placeholder, overridable via `HYBRID_LAB_PROXMOX_TEMPLATE_OVERRIDES`, same pattern as vSphere's `source_vm`) and `azure_image` (a `publisher`/`offer`/`sku`/`version` dict). `TEMPLATES`'s type hint widened from `dict[str, dict[str, str]]` to `dict[str, dict[str, object]]` to allow this.
- `api/tests/test_terraform_utils.py` (9 tests, `subprocess.run` mocked), `test_proxmox_backend.py` (6 tests, `terraform_utils.plan` mocked), `test_azure_backend.py` (7 tests, same) + `test_terraform_backends_live.py` (1 test, genuinely runs the real `terraform` binary - init + plan - against `terraform/environments/dev/proxmox` with made-up Proxmox credentials; auto-skips if `terraform` isn't on PATH). **Important finding, verified manually before writing that test:** `terraform plan` for a brand-new resource never actually contacts the remote API - there's nothing existing to refresh, and the provider only connects on an actual create/apply - so a plan against a completely unreachable Proxmox endpoint *succeeds* (confirmed with a real `terraform plan` run by hand against `https://127.0.0.1:19`, a port nothing listens on). The live test therefore asserts a genuine successful plan, not a failure. ### Design notes to carry forward

- **Backend abstraction.** `app/backends/__init__.py`'s `_BACKENDS` dict is keyed by `"vsphere"/"proxmox"/"azure"`, and all three now have a real implementation with the same "env vars present → real backend, else `SimulatedBackend`" fallback. The router and store did not need to change for Phase 3 either - the `ProvisioningBackend` abstraction from Phase 1 has held up across all three backend kinds.
- `ProvisioningError` (in `app/backends/base.py`) maps to a 502 on both create and delete - reused for `terraform plan`/`terraform init` failures too (see `terraform_utils.py`).
- The catalog (`app/catalog.py`) is the single source of truth for template → backend mapping and size → spec. `vsphere.py`'s `source_vm` + `HYBRID_LAB_VSPHERE_TEMPLATE_OVERRIDES` pattern has now been reused twice (`proxmox_template_vm_id`/`HYBRID_LAB_PROXMOX_TEMPLATE_OVERRIDES` for Proxmox, `azure_image` for Azure, no override needed there since it's not something CI needs to point at a fixture) - a solid template for whatever Phase 4's Ansible/PowerShell baselines need from the catalog, if anything.
- Metrics use a registry scoped to the FastAPI app instance (`app.state.metrics.registry`), not `prometheus_client`'s global default registry - keep doing this so future tests that spin up multiple app instances don't collide.
- **Mocking compiled PowerCLI cmdlets in Pester doesn't work** if the cmdlet has a strongly-typed parameter (e.g. `Set-VM -VM : VirtualMachine[]`) - Pester's mock preserves that type constraint, so a plain test double gets rejected before the mock body ever runs. Wrap the call in your own loosely-typed private function and mock that instead (see `Set-LabVMNotesMarker`). Only matters when adding new unit tests against real PowerCLI cmdlets, not against vcsim (vcsim tests pass real objects, no mocking involved).
- **vcsim quirk:** a VM's `VirtualPortGroup` object, once resolved via `Get-VirtualPortGroup`, can't be handed to `Set-NetworkAdapter -PortGroup` reliably - standard portgroups sharing a name across hosts also share vcsim's internal `Key` string, so PowerCLI's own re-resolution becomes ambiguous even for a single already-resolved object. Use `Set-NetworkAdapter -NetworkName '<name>'` (a string) instead, which resolves scoped to the adapter's own VM/host and has no such issue; see `New-LabVM.ps1`.
- **`terraform test` + `mock_provider` quirk:** a nested block typed as a set (Terraform's plugin SDK still represents e.g. `admin_ssh_key {}`/`source_image_reference {}` that way for some resources) can't be indexed with `[0]` in a test `assert` - use `one(azurerm_x.y.block_name).attr` instead, or `[for b in ... : b.attr if ...][0]`. Also: chaining `command = apply` through resources whose computed attributes feed into another resource's *validated* field (e.g. a mocked `subnet.id` fed into `network_interface.subnet_id`, which azurerm validates as a real Azure resource ID shape) fails, because mock_provider fills computed attributes with arbitrary mock strings, not valid-looking IDs - use `command = plan` instead when assertions only need config-known values (which covers nearly everything worth asserting on a module that renders request data into resource arguments).
